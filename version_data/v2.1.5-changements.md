# Changements V2.1.5

Ce document décrit les changements effectués depuis le tag `v2.1.4`, avec la raison de chaque modification et son effet attendu.

## Contexte

- Run concerné : `SAC_CNN_GRU_PROGRESS_v2`
- Branche : `v2`
- Config : `configs/v2.0.json`
- Objectif : obtenir des tours complets, puis conserver les meilleurs modèles selon plusieurs critères.

## Résumé

| Fichier | Changement | Raison principale |
|---|---|---|
| `configs/v2.0.json` | Épisodes de 12 min, mémoire 400k, récompense renforcée | Permettre un tour complet et pénaliser le temps/les collisions |
| `tmrl/custom/tm/utils/control_gamepad.py` | Gaz/frein binarisés | Les triggers analogiques sous ~0.7 ne fonctionnent pas dans TM2020/Proton |
| `tmrl/networking.py` | Best-checkpoint sur `max_progress` | Conserver le meilleur modèle même en cas de régression |
| `tmrl/networking.py` | Best lap et best clean lap | `max_progress` sature et ne mesure pas la vitesse |
| `version_data/v2.md` | Documentation de la config, des triggers et des résultats | Garder une trace exploitable de la version |

## 1. Allongement des épisodes et augmentation de la mémoire

### Changement

Dans `configs/v2.0.json` :

- `RW_MAX_SAMPLES_PER_EPISODE` : `2000` → `14400`
- `ep_max_length` : `2000` → `14400`
- `MEMORY_SIZE` : `200000` → `400000`

### Pourquoi

À 20 Hz, `2000` pas représentent seulement 100 secondes. Le meilleur tour connu fait environ 240 secondes, donc un épisode ne pouvait pas contenir un tour complet.

`14400` pas correspondent à 12 minutes, ce qui laisse le temps de terminer un tour même en cas de ralentissement ou de petite erreur.

La mémoire a été doublée pour conserver davantage d’expériences issues de ces épisodes plus longs.

## 2. Renforcement de la récompense

### Changement

Toujours dans `configs/v2.0.json` :

- `TIME_PENALTY` : `-0.005` → `-0.01`
- `COLLISION_PENALTY_PER_KMH` : `0.1` → `0.3`
- `COLLISION_PENALTY_MAX` : `3.0` → `6.0`
- `FAILURE_COUNTDOWN` : `10` → `60`

### Pourquoi

- Le temps est le critère final : une pénalité deux fois plus forte pousse à aller plus vite.
- Les collisions font perdre du temps et rendent les tours moins fiables : la pénalité a été triplée.
- `FAILURE_COUNTDOWN=10` terminait un épisode après seulement 0,5 seconde sans progression. C’est trop court après un départ ou un ralentissement normal. `60` pas laissent 3 secondes pour repartir.

### Effet

Les épisodes peuvent désormais aller au bout d’un tour, et l’apprentissage est davantage incité à éviter les murs et à réduire le temps au tour.

## 3. Binarisation des triggers gaz/frein

### Symptôme

Le modèle pouvait produire une action de gaz, mais la voiture ne bougeait pas. Certains épisodes restaient bloqués au départ malgré une action non nulle.

### Diagnostic

Des tests manuels et via l’environnement ont montré que TM2020/Proton :

- ignore les triggers sous environ `0.7` ;
- traite `0.7`, `0.8` et `1.0` comme la même valeur, c’est-à-dire plein gaz.

Exemples mesurés :

- `gas=0.68` : voiture immobile ;
- `gas=0.70` : plein gaz ;
- `gas=0.54` : aucun effet.

### Changement de code

Fichier : `tmrl/custom/tm/utils/control_gamepad.py`

Avant :

```python
if control[0] > 0:
    gamepad.right_trigger_float(value_float=control[0])
else:
    gamepad.right_trigger_float(value_float=0.0)
```

Après :

```python
def _digital_trigger(value):
    return 1.0 if value > 0.05 else 0.0

if control[0] > 0:
    gamepad.right_trigger_float(value_float=_digital_trigger(control[0]))
else:
    gamepad.right_trigger_float(value_float=0.0)
```

Le frein utilise la même fonction.

### Pourquoi

Le modèle sort toujours des valeurs continues, mais le jeu ne sait pas les exploiter sous `0.7`. Sans correction, une action `0.54` était perdue.

La binarisation garantit que toute intention d’accélérer ou de freiner est réellement transmise.

### Effet

- La voiture accélère dès que le modèle le demande.
- Le modèle ne peut plus doser finement l’accélération : il apprend à appuyer et relâcher.
- La direction reste analogique ; seule la paire gaz/frein est binarisée.

## 4. Best-checkpoint sur `max_progress`

### Changement

Fichier : `tmrl/networking.py`

Ajout de :

- `weights/<RUN_NAME>_best.tmod`
- `weights/<RUN_NAME>_best.json`

Le JSON contient `max_progress` et `saved_at`.

### Pourquoi

Les checkpoints périodiques peuvent être moins bons que des modèles précédents. Sans best-checkpoint, un bon modèle peut être perdu après une phase de régression.

Le critère `max_progress` a été choisi en premier car il est simple et directement lié à l’objectif “aller plus loin sur la piste”.

### Limite

`max_progress` sature autour de `1.0`. Une fois qu’un tour est terminé, un tour plus rapide peut avoir un `max_progress` égal ou légèrement inférieur. Il ne serait alors pas sauvegardé.

C’est cette limite qui a motivé les best lap et best clean lap.

## 5. Best lap et best clean lap

### Pourquoi

`max_progress` répond à “jusqu’où la voiture est allée”, pas à “à quelle vitesse elle a terminé”.

Deux critères séparés sont donc nécessaires :

- **best lap** : le tour fini le plus rapide, même avec des collisions ;
- **best clean lap** : le tour fini le plus rapide sans aucune collision.

Le best clean lap est particulièrement utile pour conserver un modèle capable de rouler proprement, pas seulement vite.

### Fonctionnement

Fichiers ajoutés :

- `weights/<RUN_NAME>_best_lap.tmod`
- `weights/<RUN_NAME>_best_lap.json`
- `weights/<RUN_NAME>_best_clean.tmod`
- `weights/<RUN_NAME>_best_clean.json`

Champs JSON :

- `lap_steps`
- `lap_time_s`
- `collisions`
- `max_progress`
- `saved_at`

Règles :

- un tour doit être terminé pour être éligible ;
- le best lap est comparé sur `lap_steps` ;
- à nombre de pas égal, moins de collisions gagne ;
- le best clean lap exige `collisions == 0` ;
- un checkpoint n’est mis à jour que si la sauvegarde des poids et du JSON réussit.

### Détection d’un tour fini

Dans `collect_train_episode` :

```python
finished = bool(info.get("end_of_track", False)) or (
    terminated and max_progress >= 0.999
)
```

Les collisions sont comptées à partir de `info["collision"]`.

Le temps est récupéré depuis `info["race_time_s"]` s’il est disponible et positif. Sinon, il est estimé avec `steps * time_step_duration`.

### Pourquoi ces choix

- `lap_steps` est déterministe et directement comparable, indépendamment du temps réel ou des arrondis.
- Les collisions servent de départage à temps égal.
- Le best clean lap est séparé pour ne pas être écrasé par un tour plus rapide mais sale.
- Le JSON permet de recharger l’état au redémarrage du worker.

### Initialisation du best lap actuel

Le best `max_progress` existant a été copié vers `_best_lap.tmod` pour ne pas perdre le meilleur tour déjà connu.

Valeurs initialisées :

- épisode : `312`
- `lap_steps` : `4799`
- `lap_time_s` : `239.950`
- collisions : `4`
- `max_progress` : `0.9999669790267944`

Le best clean lap n’a pas pu être initialisé : le tour propre de l’épisode `311` (`4:21.85`, 0 collision) n’a pas de poids séparés disponibles. Il sera créé au prochain tour propre.

## Limites et suite

- Le training en cours au moment de ces changements utilise encore l’ancien code ; un redémarrage du worker est nécessaire pour activer les nouveaux best-checkpoints.
- `_best_clean.tmod` sera créé au prochain tour terminé sans collision.
- La binarisation gaz/frein supprime le dosage fin. C’est acceptable tant que le jeu ignore la plage basse, mais une rampe `0.7 → 1.0` pourrait être testée plus tard.
- La deadzone de direction n’est pas compensée.
- Le best lap est priorisé sur `lap_steps` ; `lap_time_s` est informatif.
